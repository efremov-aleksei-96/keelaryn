# VPS MIGRATION — единый исполняемый план KeelarynOS

**Статус:** ACTIVE · 2026-11-17. **Владелец плана реализации:** Keelaryn Engine, репозиторий `efremov-aleksei-96/keelaryn`, ветка `dev/mcp-portability`. **Единственный курсор перехода:** этот файл. `mcp/README.md` содержит инженерные доказательства и ссылку сюда, но не вторую очередь задач. Общие правила — `KEELARYNOS_PROJECT_RULES.md` по официальной ссылке проекта ChatGPT; предметные правила и решения о переключении — только у соответствующих Domain OS/проектов. Этот план **не** делает Keelaryn Engine владельцем чужих данных.

## Результат, который требуется получить

**Решение 2026-11-17:** работа продолжается на восстановленном текущем VPS; подбор, покупка и перенос на новый хост отложены из-за бюджета. Для будущего переезда реализация должна допускать перенос без переписывания доменных канонов: исходники в GitHub; конфигурация сервисов/скоупов и системные зависимости документированы; секреты не входят в код/экспорт; рабочие файлы и G1-журнал восстанавливаются побайтно; пути, UID и адрес сервера не должны быть зашиты в состояние проектов. Реальная проверка чистого хоста, восстановление служб/туннеля и внешних копий ещё НЕ выполнены. Это целевой критерий, не разрешение сейчас мигрировать или покупать.

VPS хранит единственные активные версии разрешённых файлов проектов в понятном локальном дереве. MCP даёт ограниченные операции чтения/записи с CAS, журналом и человеческим CLI; всё повторяемое работает без ChatGPT. Google Drive перестаёт быть **операционной зависимостью** канонических проектов и может оставаться внешней резервной копией / историческим оригиналом. **Полный отказ от Google даже для резервирования** — отдельный завершающий выбор независимого хранилища, а не обещание уже достигнутой автономности. GitHub остаётся владельцем исходников Keelaryn Engine, специальные внешние функции — явно описанные исключения.

**Запрещено считать переходом:** простое копирование; подключение read-only snapshot; изменение одного проекта без проверки всех его зависимостей; назначение двух действующих канонов; экспорт из Sheets без сохранения формул, колонок, истории и семантики; проверку на VPS вместо доказанной работы на независимом ПК. **Bankruptcy: MANUAL_LOAD_ONLY** — не открывать, не включать в инвентаризацию содержимого и не переносить без отдельной прямой команды.

## Обязательная стратегия: сначала один ПОЛНОСТЬЮ работающий пилот, потом проекты целиком

**Решение пользователя 2026-11-15 (приоритетное для дальнейшего выполнения):** не переносить множество проектов и не переключать отдельные документы внутри рабочего проекта «по мере готовности». Сперва создать и довести **один изолированный, некритичный пилотный проект** на VPS до законченной ежедневной работы **без Google Drive как рабочего источника**. Только после успешного полного цикла разрешается последовательная миграция **проект за проектом**, а не файла за файлом. Слова «перенести» и «готов» применяются к проекту лишь после полноценной проверки его штатной деятельности на VPS, включая все обязательные данные и зависимости.

**Сохранить непрерывность текущей работы:** `ArmenianLearning`, `EnglishOS`, а также оставшиеся активные части `MusicLibrary` не переключать и не копировать для дальнейшего переключения во время пилотной инженерной работы. Продолжать их штатное использование через текущих владельцев и текущие каноны, без двойной записи. Для MusicLibrary уже исторически переключены **только** `PROJECT.md` и `STATE.md`: это **частичный ранее выполненный cutover**, а НЕ миграция всего MusicLibrary. Их действующий VPS-канон не откатывать и не создавать новые активные Drive-копии без отдельного решения; музыкальный Registry, каталог записей и специализированные контракты остаются у прежних владельцев. Других частичных cutover не создавать.

**Что должен уметь законченный VPS-пилот до допуска реальных рабочих проектов:**

1. Человек и ChatGPT могут найти все правила, состояние, курсор и данные проекта **на VPS** через точный локальный путь и MCP, без обязательного Google Drive для загрузки/чтения/изменения.
2. Реально работают операции чтения, поиска, создания в пределах владельца, точечного обновления/добавления, поддержка больших Markdown/CSV/JSON, безопасная запись по SHA-256 CAS, идемпотентный повтор после неизвестного результата, а также несколько связанных файлов одного логического шага. Для последнего — явная безопасная последовательность и восстановление после частичного сбоя (не выдавать несколько CAS за транзакцию).
3. Изолированные полномочия каждого владельца: deny-by-default, предсказуемые allowlist и локальные каталоги, отсутствие доступов к чужим проектам/секретам; в журнале достаточно сведений для разрешения незавершённого изменения, без бесконтрольного накопления.
4. Реальный сценарий «мобильный чат → MCP → изменение → повторное чтение → продолжение после нового подключения» и независимый человеческий способ запуска/чтения без ИИ. Обычная эксплуатация не зависит от Drive; резервное копирование в Drive пока допустимо как **отдельная сетевая зависимость**, не обязательная для чтения/записи, а восстановление из внешней копии должно быть продемонстрировано.
5. Проверены права и ограниченные ресурсы, изолированное восстановление проекта со всеми необходимыми данными и понятный точный NEXT. Тестовый проект не должен становиться вторым каноном работающего предметного проекта.

**Порядок после пилота:** выбрать **один целый малорисковый проект, которым пользователь сейчас активно не пользуется**; инвентаризировать его настоящий полный состав (включая вложенные файлы, таблицы, связи и оригиналы); защитить оригинал; перенести и сверить всё необходимое; отдельно подтвердить разрешение на cutover; кратко исключить одновременную запись в обе стороны; изменить маршруты и ссылки у владельца; выполнить реальную штатную операцию только через VPS; только тогда пометить проект `MIGRATED / VPS-ONLY OPERATION`. Если логическая работа проекта не поддерживается VPS — **оставить проект на Drive целиком**, устранить блокер в тестовом пилоте и продолжить другие независимые инженерные задачи.

**Заморозка кандидатов на период пилота:** `ArmenianLearning`, `EnglishOS`, весь оставшийся `MusicLibrary` — `FROZEN_FOR_CUTOVER / KEEP_WORKING`. Эта заморозка касается только миграционных переключений, **не** обычных занятий и музыкальной работы. Не использовать их текущие данные как синтетический тест и не переносить для «подготовки» на VPS без необходимости. Предыдущая инвентаризация ArmenianLearning остаётся исторической, но не означает разрешённый ближайший перенос.

## Правило исполнения для любого нового чата и команды «Далее»

1. Открой этот файл, действующие общие правила по ссылке проекта ChatGPT и только затронутые актуальные источники; повторно не читай неизменённое. Перед изменением сверяй реальное состояние. Не требуй ручной работы, если доступен безопасный API.
2. Выбери **первую выполняемую** задачу из таблицы ниже с учётом зависимости и риска. `READY` — выполняй; `BLOCKED` — **запиши конкретный блокер и переходи к следующей независимой задаче в том же ходе**; `DONE` не повторяй; `WAIT` не блокирует параллельные независимые действия. Одновременно не делай массовую миграцию.
3. До завершения **одного полного изолированного VPS-пилота** не начинать cutover других проектов. Затем для **целого** нового предметного владельца: текущий канон → полный обязательный состав/зависимости → защита оригинала → перенос и сверка → независимое восстановление → **отдельно разрешённое переключение целого проекта** → проверенная штатная операция только через VPS и исправление ссылок → повторное чтение → единое резервирование. Не допускать одновременной записи в Drive и VPS. Старые Drive-файлы сохраняй как исторические.
4. После существенного результата **обнови этот же курсор** (статусы, краткое доказательство, блокер, точный NEXT) и перечитай запись. При неопределённой записи сначала read-only reconcile, никакого слепого повтора. Не делай отчётов и новых параллельных планов.
5. Если нет доступа к одному сервису, источнику или разрешению — переходи к независимой подготовке следующего этапа. **Никогда не трактуй один блокер как остановку всей миграции.** Не обещай фоновую работу: новые ходы начинаются по запросу или через отдельно созданную явную автоматизацию.
