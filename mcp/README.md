## Local directory read-only scope — implemented, synthetic-verified

In `KEELARYN_MCP_MODE=local`, an operator-owned scope registry may contain a `local-ro` entry. Example **configuration only** (replace the root with a real directory owned by the unprivileged service user; do not point this at important data before independent validation):

```json
{
  "schema": "keelarynos_mcp_file_scopes_v1",
  "scopes": {
    "synthetic": {
      "backend": "workspace",
      "access": "read-write",
      "description": "Ephemeral synthetic-only benchmark files"
    },
    "NotesPilot": {
      "backend": "local-ro",
      "access": "read-only",
      "snapshot_only": false,
      "canonical": false,
      "root": "/home/USER/keelaryn-pilot",
      "allow": ["docs/", "PROJECT.md"]
    }
  }
}
```

The `synthetic` entry is **still mandatory** under the inherited registry schema and only controls the isolated benchmark workspace; it is **not** access to real projects. No secrets or live folder data are stored in Git.

The MCP caller can select only the preconfigured project and relative paths. A `local-ro` root must be a canonical absolute path owned by the effective unprivileged user, without group/other write access. Config must be owned by that user and private. Ancestors and nested directories are checked; root and child symlinks are rejected using directory descriptors and `O_NOFOLLOW`. Files must be ordinary, single-link, user-owned, non-group/world-writable UTF-8 `.md`, `.csv`, or `.json`. Relative segments use the existing conservative ASCII naming restrictions and additionally reject hidden/sensitive names. Exact files or directory prefixes may be allowlisted; blanket root access is not accepted.

The backend supports `list_files`, `read_files` (including existing character paging) and `search_files`. `edit_files` and `delete_files` are denied regardless of arguments. A single document is capped at 64 KiB, reads at 256 KiB total, and each directory listing at 1000 entries. Search now also has **global** caps of 100 read documents, 100 visited directories and 1000 visited directory entries. When a global search cap is reached, it reports `truncated`; directories exceeding the per-directory limit fail closed. Search traverses open descriptor-relative child directories under a single pinned root descriptor; a multi-file read likewise pins the root. The file reader now compares permissions, owner and link count before/after reading, in addition to size and timestamps.

This protects the tested path boundaries, but **does not create a transactional snapshot** or defend against every in-place rewrite by another process sharing the same user identity. Concurrent writes, mount/bind-mount manipulation, broader adversarial environments, and host-specific permission cases are **not fully qualified**. The `canonical` flag is operator-declared metadata; it does not prove a local copy is current.

### Targeted safety audit — verified 2026-11-12

**Confirmed findings and fixes:**

1. The previous search only limited *read files*; arbitrarily many empty directories or name entries could still be visited. Fixed with global directory/entry budgets in `src/local_ro.py`.
2. The previous search reopened the configured root by pathname for each recursive directory, potentially mixing two distinct same-owner roots if the pathname was replaced while a search ran. Fixed with a root FD pinned for the whole search and parent-FD-relative directory traversal; batched reads now pin their root too.
3. The previous file reader did not compare mode/owner/link-count metadata *after* reading. Now compares them with the initial `fstat` (in addition to length, mtime and ctime). This detects observed changes but is not proof of immutable content under all concurrent writers.

**Adversarial tests** in existing `tests/test_local_ro.py` deterministically replace a file or directory with a symlink at the moment of `open`, and swap the root pathname after initial enumeration. The symlinks fail to open; the pinned-root search ignores the replacement tree. Tests also check read size 64 KiB, batch size 256 KiB, 100-file search cap, 100-directory global cap, 1000-entry global cap, 1000-entry per-directory rejection, allowlist denial, unsafe file/directory/config permissions, no edit/delete, and no changes to the synthetic originals.

## Minimal target contract (PARTIALLY IMPLEMENTED)

- **Operator-defined paths (implemented for current entrypoints):** `KEELARYN_MCP_CONFIG` selects the scope registry and `KEELARYN_MCP_STATE_DIR` selects the state root, preserving previous VPS absolute paths as defaults. A user-supplied MCP request cannot select its own filesystem root.
- **Two safe ownership profiles (limited implementation):** system installation retains root-owned configuration and systemd sandboxing; local mode requires an unprivileged caller and a private user-owned configuration/state root. Local stdio and `local-ro` were verified only with synthetic fixtures. The validated path boundaries reject unsafe ownership, group/other writes and symlink traversal; further adversarial review remains required.
- **Explicit scopes:** unlisted projects are inaccessible; real sources default to read-only; exact allowed roots and relative paths, file types, maximum read sizes and operation limits are enforced by the server. Do not expose arbitrary command execution or a shell tool.
- **Transport:** direct `stdio` is the baseline. Optional OpenAI Secure MCP Tunnel launches the same Python server as a child process. No public inbound port, database, Docker, web dashboard or second long-lived MCP daemon is required.
- **VPS supervision:** one systemd service, with `DynamicUser`, `StateDirectory`, `ProtectSystem=strict`, `ProtectHome`, `NoNewPrivileges`, `UMask=0077`, and secrets passed via systemd `LoadCredential`. For a stdio tunnel binding, **never run two tunnel-client instances against the same tunnel ID concurrently**.
- **Writes:** creation must fail if a target exists; replacement and deletion require a content/version precondition and an effective *atomic* protection from concurrent writers for that backend. The current check-SHA-then-`os.replace` approach is NOT general compare-and-swap against independent concurrent writers. Multi-file atomicity is not guaranteed. Real canonical sources remain read-only until backend-specific conflict safety and authorized ownership are proven. Google Drive write remains disabled.
- **Offline scope:** local Markdown/CSV/JSON can be worked with without any provider after a separately validated clean install. Cloud-origin content and remote connectors require a network; format portability does not imply an up-to-date local mirror.

## Minimal deployment design

1. Clone or obtain a fixed source revision; use Python 3.12 and stdlib for the file core. No PyPI dependency is needed by the copied Python modules.
2. For local use, pass a user-owned restricted config and state location and launch MCP stdio from the client. The `local-ro` backend is implemented and tested with synthetic directories; no live local canonical scope is authorized or validated.
3. For VPS/ChatGPT, install the verified Python source and a root-owned scope registry, then configure a **single** protected systemd service that supervises the pinned OpenAI tunnel (when required) and its Python child. Provide secrets separately; do not check them into source control.
4. Verify with synthetic data before enabling any real source; do not alter or switch the production VPS until a separate install and rollback have passed.

A fresh Linux installation is accepted only when: stdio initialize/discovery and all five tools work; invalid paths and permissions fail closed; read/write concurrency controls are proven in the allowed scope; source/config/state separation survives restart; systemd privilege restrictions and recovery work; no personal/canonical data are used in mutable tests; Windows Manager identity and behavior are unchanged.

## Concurrent synthetic edit/delete — cross-process precondition repair (2026-11-12)

**Scope:** only `mcp/src/fs_tools.py` synthetic workspace `edit_files`/`delete_files` and regression cases in the existing `mcp/tests/test_local.py`; no real project writes, no service installation or configuration change.

**Confirmed before fixing:** using a temporary `nobody`-owned synthetic workspace on the existing VPS, two separate Python processes targeted `race.md` with the **same original SHA-256**. A deterministic pause immediately before the first process's final syscall allowed the second to act:
- **edit/edit:** both clients returned success, but the first overwrite silently discarded the second's completed content (`OLD_EDIT_RACE`, final `first-write`).
- **delete/edit:** another client replaced the file successfully after the first client had rechecked the old hash, yet the first client then unlinked the replacement (`OLD_DELETE_RACE`, final `ABSENT`).
The earlier second hash check did **not** provide atomic compare-and-swap. These are proven cooperative-client lost-update/deletion races, not confirmed damage to real projects.

**Minimal fix:** `edit_files` and `delete_files` acquire Linux `flock(LOCK_EX)` on an already-validated, descriptor-open **synthetic workspace directory** for the entire SHA precondition/read/commit/verification operation, then release the lock and close the FD in `finally`. The existing `_edit_files_locked` and `_delete_files_locked` bodies keep their content/size/path/SHA validation and per-file publication semantics. **No persistent lock file, new directory, daemon or dependency outside the Linux standard library** is needed. The new lock is shared across independent MCP processes opening the same workspace inode.

**Verified after fixing:** cloned development source at commit `523f6fa04ffa6b6ec49cbd8dec585c32dcf223a2` into disposable `/tmp` and ran both existing test scripts as unprivileged `nobody`. The new forked-process barrier test `SYNTHETIC_CONCURRENT_EDIT_DELETE_PRECONDITIONS_PASS` paused one client immediately before replace/unlink while another tried to edit from the same original hash. In both interleavings the contender waited for the directory lock, then failed its stale-SHA check; exactly one operation succeeded, with the expected final content/absence and no leftover temporary files. Also passed `PYTHON_AST_PASS 8`, `MCP_FIVE_TOOL_SCHEMA_RUNTIME_ALIGNMENT_PASS`, `SYNTHETIC_DIRECTORY_ENUMERATION_BOUNDS_PASS`, `SYNTHETIC_SEARCH_TRAVERSAL_BOUNDS_PASS`, `BENCHMARK_DEFAULT_HIDDEN_AND_DENIED_PASS`, `BENCHMARK_EXPLICIT_OPT_IN_PASS`, `BENCHMARK_DIRECT_PATH_SECURITY_PASS`, `BENCHMARK_DIRECT_LIFECYCLE_PASS`, `LOCAL_STDIO_SYNTHETIC_SMOKE_PASS`, `LOCAL_RO_ADVERSARIAL_LIMITS_PASS` and `LOCAL_RO_MCP_INTEGRATION_PASS`. Temporary cloned sources and fixtures were removed; the running service remained active at MainPID `2636967`.

**Boundary and limitations:** `flock` is **cooperative, Linux-specific advisory locking**; a different same-UID process writing directly to files while ignoring the lock, mount manipulation, and malicious directory replacement are **not proven safe**. 2. **User OAuth `drive.file` + explicit Google Picker selection: viable per-file *reach*, but not strict read-only.** Google documents that `drive.file` is non-sensitive and makes app-created or user-selected/opened files available; it can **modify** those selected files. Never move all projects in one operation.

### 2. MCP data-plane contract and minimum privilege

- Start with the currently running **three-tool read-only baseline**; do not enable writes globally or for all owners. Introduce an **opt-in separately reviewed project mutation path** only for an allowed test owner first, then one authorized real owner. Separate read and write capabilities/server-side permissions. A client-side confirmation or cached tool list is **not** a security boundary; the service must deny unauthorized owner, file, tool or action even for a direct cached call. Never expose arbitrary shell, unrestricted filesystem, generic `exec`, directory recursion, credentials or another owner by default.
- Owner-specific root + exact scope allowlist; reject `..`, absolute paths, symlinks/hardlinks, filesystem mounts escaping the root, wrong UID/mode, device/special files, unsafe MIME/UTF-8/oversize, path collision, hidden sensitive folders and multiple authorized owners in one call. Keep strict systemd `DynamicUser`, `ProtectSystem`, protected credentials and only necessary read/write paths. Test Linux permissions **inside systemd isolation**, not just as `root` or `nobody` in a disposable process.
- Writes require **expected current SHA/version (compare-and-swap)**, an idempotency/request identifier, explicit owner/target/action, operation-size/count limits, checked single-file temp write in the *same directory/filesystem*, file `fsync`, atomic rename, parent-directory `fsync` where supported and a subsequent authoritative readback. Protect against concurrent writers and interrupted/unknown-outcome responses; on retry, first reconcile current bytes/version, **never blindly repeat**. A multi-file change is *not* atomic merely because single-file rename is. Reject destructive or mass operations unless independently approved, backed up and restorable. Keep material decision/evidence/NEXT with the owning project; avoid duplicate STATE/WORKLOG and bulky global audit files.
- Validate authentication, tunnel and client action-approval settings independently; existing personal plugin permissions may allow more actions than the server. When a write tool is eventually exposed, review the live permission model and intentionally require confirmation appropriate to impact. Limit per-tool capabilities, CPU/memory/time/file counts and request rate based on observed load; `MemoryMax=infinity` is a **known unbounded risk**, not a safe target. Pin release hashes and keep one Tunnel ID/one live service with a tested rollback; never enable parallel same-ID clients.

### 3. Backup is separate from MCP and survives ChatGPT failure

- **Source:** only the VPS's committed, owner-authorized canonical data and essential readable reconstruction manifests/scripts, plus necessary original evidence. Exclude runtime scratch, derived indexes, local credentials, raw tokens and transient copies. Inventory and measure size/changes and available space **before** selecting schedule/retention. Last observed root filesystem: roughly **63 GiB total, 51 GiB available**; this does *not* imply the migrated corpus fits.
- **Mechanism:** independent VPS-side snapshot process (e.g. a dedicated systemd timer) running **without ChatGPT or MCP**, using a separate least-privilege backup identity. Upload **client-side encrypted, integrity-protected, versioned** snapshots to a **dedicated Drive backup folder**. The backup identity may write only its own destination, not read private user-wide Drive or grant MCP read/write access to Drive. Encryption/decryption/recovery credentials must be protected off the VPS and outside the same Drive repository; otherwise VPS loss or one compromised credential can render backups useless. Keep an accessible human recovery runbook with tool version, repo/restore instructions, key custody, expected data owners, manifest and verification steps **without embedding secrets**. Any privileged Drive sharing/OAuth action needs separate explicit approval.
- **Candidate tool, not installed/selected yet:** Kopia offers encrypted snapshots, repository verification and a Google Drive backend, but its **native Google Drive backend is experimental**; its Rclone integration is also marked experimental. Compare provider scope, key custody, full restore, storage costs and failure behaviour before choosing—not a claim that the user's existing Windows Kopia or historical `C:\D0_DisasterBackup_Kopia`/`E:\D0_DisasterBackup_Kopia` repositories work for the VPS. Official: https://kopia.io/docs/repositories/ and https://kopia.io/docs/advanced/consistency/ . Another supported backend/tool may be preferable if testing warrants it; avoid stacking Kopia + Rclone + a bespoke sync unless necessary.
- **Backups must be restorable and independent:** successful upload/metadata or checksum alone is not evidence of restoration. Validate listing, file-level integrity, decryption and *selected complete clean-directory restoration* including filenames, owner mapping, ACLs, exact bytes/SHA, symlinks policy and resume state. Then rebuild a disposable MCP read-only service from documented sources and verify old versions can be restored. Check backup age, rotation/retention, failed/partial uploads, long outages, out-of-space, interrupted snapshots, provider removal, key compromise, deletion/ransomware and quota exhaustion. Stronger protection against backup-account deletion/rewriting is needed before any high-value private data rely on a single Drive repository: independently held recovery copy or a proven retention/immutability mechanism as acceptable. Never delete old source/backup solely due to a successful upload.
- **RPO/RTO are not currently measured.** Propose backup freshness objectives only after an owner-specific loss budget and test. For an initial *low-volume* owner, a daily encrypted incremental snapshot and bounded retention could be a starting point, but a 24h schedule implies **up to about a day of lost work** after VPS destruction. Sensitive or rapidly changing owners may require more frequent versioned backups; don't silently apply one retention setting to every project. Prefer alert only on actionable failures and checks that prove recoverability. Existing daily `MCP → Google Drive backup` targets **synthetic benchmark data only** and does not qualify as a production backup, must not be repurposed or changed here.

### 4. Ordered safety gates — tests first, migration only after proof

Each gate must state **PASS / FAIL / NOT_TESTED**, exact source/version, scope, evidence and stop/rollback action **inside this README for Engine** or the affected owner's canonical source. Don't create a second log by default. Synthetic PASS never becomes a real production PASS. Do not mechanically run all tests daily: run them before significant migration/risk, on changed contracts, or after a detected failure.

**G0 — Source/owner inventory (MUST before one real owner):** read that owner's current canonical entrypoint/contract, real paths/size/file types, links/formulas/original evidence, effective permissions, privacy and special exclusions; assess expected load, disk/inode/backup limits and dependencies. Mark Drive/source data **active** and any proposed VPS copy **staged**; preserve raw originals and read-only rollback. Do not scan or migrate `Bankruptcy` without direct authorization.

**G1 — Synthetic project data plane (MUST before real writes):** in a disposable VPS test root, exercise MCP list/read/search and the *new* owner-scoped create/edit/rename/delete API with auth and positive/negative scope cases; atomic commit and exact readback, concurrent compare-and-swap collision, retry with same request ID, interrupted call and unknown outcome, invalid input, traversal/symlink/hardlink, disallowed UID/mode, oversized UTF-8/CSV/JSON, disk full, timeout, service restart and attempted direct write despite tool-list restrictions. Confirm existing synthetic snapshot/public scopes cannot be written by the new route. Never call a synthetic PASS proof of production durability.

**G2 — Synthetic backup/recovery loop (MUST before first real canonical switch):** take a consistent snapshot of test owner data, verify encrypted artifact/version/index and metadata, simulate unavailable network and partial upload, restore into a **separate empty directory without Google Drive UI or ChatGPT**, compare every expected SHA/path/schema and project NEXT, then prove a newly started test service can read the restored dataset. Demonstrate recovery of one older snapshot and an unusable key/broken artifact case; keep evidence and stop on any ambiguity. Real Drive integration and destination ACL remain **NOT_TESTED** until explicitly authorized.

**G3 — VPS isolation and production-like staging (MUST before service switch):** pin exact dev commit and installed binary/profile/tunnel ID, inspect systemd `ExecStartPre` and live scopes, resource quotas, credential mounts, secret leakage and log permissions, single-tunnel exclusivity, pre-existing drop-in/rename collisions, root paths and backup locations. Test a faithful unprivileged/systemd staging environment and a stop→switch→start→health→stop→restore→start rollback (against a *disposable test service*, not the live one) including stale tool definitions and denied writes. Keep complete original code/config/scope/credential **references** and rollback without copying secrets into GitHub.

**G4 — One-owner staging reconciliation (MUST before authority transfer):** with separate explicit approval for that owner only, transfer its files from the actual verified current canon to *staged noncanonical* VPS paths, preserve all provenance and originals. Compare source/version/freshness, file count, sizes, SHA-256 byte-for-byte where applicable, link targets, Markdown readability, CSV encoding/columns, JSON schema, XLSX formulas, attachments and special contract cursors. Handle native Google formats by explicit approved conversion with functional comparison, never by assuming `.md` text is interchangeable. Record failed/ambiguous items, do not switch them.

**G5 — Restore-backed single-owner cutover (MUST, separately approved):** verify actual external encrypted backup and real restore of the **staged owner**, freeze/serialize source writes for a brief maintenance interval, reconcile last source revision, switch exactly one owner routing/canonical entrypoint to VPS, then prove all read/write/continuation operations work through ChatGPT→MCP and *without* ChatGPT using local files. Archive/mark old Drive source noncanonical/read-only, without deleting it or introducing a second writable canon; update the actual KeelarynOS/domain owner contract **only at the proven switch**. On any failure or conflicting partial switch, stop new writes, inspect actual state and restore prior authority with explicit version reconciliation. A partial migration does not count.

**G6 — Failure/security acceptance for the migrated owner (MUST):** test owner-to-owner denial, expired/revoked credentials, offline client, inaccessible Google backup, VPS restart, connection loss, concurrent edits, malformed server output, unauthorized file mutation, scope expansion, missing/corrupt snapshot, restoration without ChatGPT/previous chats and correct human NEXT. Ensure a compromised backup credential cannot become a project-writer credential. Capture the exact tested conditions; never claim unrestricted autonomy.

**G7 — Operational operation (after proof):** run backups independently of ChatGPT, check fresh backup+failure notification, verify a small restore sample at risk-appropriate intervals and a full restore after any major migration or incident. Monitor filesystem space, inode/IO exhaustion, memory, TLS/tunnel health, secret age and backup retention with simple threshold alerts. Avoid duplicate reporting and compulsory full A/B/C audits. Only add more infrastructure when an observed failure mode justifies complexity.
